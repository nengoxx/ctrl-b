# R28 — The installed PWA icon's backdrop: why it's a white box, and what it can be instead

**Date:** 2026-08-11 · **Class:** web-platform / platform-integration research (Android launcher +
browser install paths), with a small **measured** peer-manifest sample. Not a peer-class pass — the
question is a platform question, and the in-class peers turned out to be evidence *against* rather
than a model (§6).

**Question (owner):** ctrl-b installs as an app on the owner's Android phone. The installed
home-screen icon renders as the blue cat **on a white box**, while the pre-install *bookmark* icon
rendered borderless. **Can the installed icon have a transparent background like the bookmark did —
and if not, what is the best-looking achievable state?**

**Established going in (not re-researched):** all four shipped PNGs — including
`icon-maskable-512.png` — have a fully transparent background; the manifest ships
`theme_color`/`background_color: #0a0a0d`, `display: standalone`, three `purpose:any` icons
(192/256/512) and one `purpose:maskable` (512); icons are generated by
`frontend/scripts/gen-pwa-icons.mjs` from `frontend/src/assets/vapor-logo.png`. Which browser
performed the successful install was **unknown** — §5 settles it by construction.

**Related:** `docs/MEDIA_PLAN.md` (D53, the art namespaces) · `frontend/vite.config.ts` (the
manifest block) · `frontend/index.html` (the `rel=icon` / `apple-touch-icon` links) ·
[R10](./R10-web-push-stack.md) (the same device, Fennec-vs-Chrome branch).

## 0. Headline

1. **No. A genuinely transparent installed icon is not achievable on Android, and the spec says so
   normatively** — not the launcher, not a bug: *"If the icon contains transparent pixels, the user
   agent **MUST** composite the icon onto a solid fill (e.g., white) of the user agent's choice."*
   (W3C App Manifest §2.3, **VERIFIED**, quoted in §2). Every install path we can reach composites.
2. **The white specifically comes from Chrome's WebAPK shell, not from the launcher and not from
   `background_color`.** The WebAPK template's own launcher icon is
   `<adaptive-icon><background android:drawable="@color/white_adaptive_ic_launcher_background"/>` and
   that colour is literally `#FFFFFF`; the maskable icon is only the **foreground** layer
   (**VERIFIED**, Chromium `main`, §3.2). A transparent foreground therefore *is* a white box, by
   construction. A second, launcher-side white source exists for non-adaptive icons
   (AOSP `BaseIconFactory.DEFAULT_WRAPPER_BACKGROUND = Color.WHITE`, **VERIFIED**).
3. **Both browsers pick our maskable 512 for the home-screen icon.** Chrome sets
   `prefer_maskable_icon = true` for add-to-home-screen; Firefox for Android sorts maskable resources
   **first** in its icon comparator (**VERIFIED**, §3.1 / §5). So one file — `icon-maskable-512.png` —
   controls what the owner sees on both paths.
4. **Firefox for Android does honour `purpose: maskable` today, and it composites onto the manifest's
   `background_color`, not white** (`ColorProcessor` → `AdaptiveIconProcessor.drawColor`,
   **VERIFIED**, §5). Since ours is `#0a0a0d`, a Firefox install could not have produced a *white*
   box ⇒ **the successful install was Chrome's WebAPK path** (inference, §5.3).
5. **The fix is the one the field already ships: full-bleed *opaque* maskable, transparent `any`.**
   Measured on live sites: X `any` = transparent / X `maskable` = 100 % opaque black; Squoosh `any` =
   transparent / `maskable` = 100 % opaque `#3D3F3F` (**VERIFIED by pixel measurement**, §6). web.dev's
   maskable article says the same in words and explicitly warns against `"any maskable"`.
6. **Our maskable art is also too big for the new backdrop.** It occupies **0.779** of the canvas —
   legal (the safe-zone circle is 0.8 diameter) but the *maximum* legal, i.e. ~89 % of the visible
   tile. The two peers measured sit at **0.598–0.615**. Recommend **0.62** (§8).
7. **Themed (`monochrome`) icons: not worth shipping.** The WebAPK adaptive-icon XML has no
   `<monochrome>` layer at all, and Firefox consumes `monochrome` only for the PWA's *site-controls
   notification*, never the launcher icon (**VERIFIED**, §7).
8. **iOS is a separate, real bug:** `apple-touch-icon` points at the transparent `icon-192.png`;
   iOS fills transparency with black (**REPORTED** — no Apple normative text found, §8).
9. **Gotcha that will bite the verification:** an already-minted WebAPK does **not** pick up a changed
   icon promptly. Chrome re-checks at most once a day (`UPDATE_INTERVAL = 1 day`, or 30 days when
   relaxed), and an icon-hash change triggers an **App Identity Update dialog** the owner must
   approve (**VERIFIED**, §9.2). Uninstall + reinstall is the deterministic path.

## 2. What the spec actually mandates (Q1 normative half, Q3)

**Source: W3C Web Application Manifest, §2.3 "Icon masks and safe zone"**
(<https://www.w3.org/TR/appmanifest/#icon-masks>) — fetched 2026-08-11, **VERIFIED**, verbatim:

> The **safe zone** is the area within a maskable icon which is guaranteed to always be visible,
> regardless of user agent preferences. It is defined as **a circle with center point in the center
> of the icon and with a radius of 2/5 (40 %) of the icon size**, which means the smaller of the icon
> width and height, in case the icon is not square.

> The user agent MAY apply a mask of any size, making any pixels that are more than 2/5ths of the
> image size … away from the center (the safe zone) transparent.
> The user agent MUST NOT make any pixel within the safe zone transparent.
> The user agent MAY enlarge the icon by adding additional padding.
> **If the icon contains transparent pixels, the user agent MUST composite the icon onto a solid fill
> (e.g., white) of the user agent's choice.**

> Note: It is suggested that designers avoid using transparent pixels in maskable icons.

> Note (§2.3.1): By staying inside the safe zone, most icons will have around **10 % padding on the
> top, bottom, right and left** with no content or non-essential content…

**So the exact geometry to pin (Q3):** safe zone = centred circle, **radius 0.40 × canvas**
(diameter 0.80). Practically: full-bleed opaque background edge-to-edge, all essential art inside
the centred 80 %-diameter circle, ≈10 % dead margin per side.

**Practical convention (web.dev, Google, authored around the same spec work —
<https://web.dev/articles/maskable-icon>, last updated 2019-12-19, **VERIFIED** verbatim):**

> Because maskable icons need to support a variety of shapes, you need to supply **an opaque image
> with some padding** that the browser can crop…

> The important parts of your icon, such as your logo, must be within a circular area in the center of
> the icon with a radius equal to **40 % of the icon width**. The outer 10 % edge might be cropped on
> some platforms.

> The `purpose` field tells the browser how your icon should be used. By default, icons have a purpose
> of `"any"`. **In Android, these icons are resized on a white background.** … To make an icon
> maskable, set its purpose value to `"maskable"` … **This removes the white background** and gives you
> more control over the icon's appearance.

> **Caution:** We don't recommend using multiple purposes for maskable icons. Using maskable icons as
> `any` icons adds unnecessary padding… **We recommend designing `any` icons like your site's favicons,
> with transparent regions and no extra padding.**

That last paragraph is the direct answer to Q4's "standard practice" question, from the platform's own
guidance: **`any` stays transparent, only `maskable` goes full-bleed opaque.**

## 3. Chrome / WebAPK path (Q1, Q2)

### 3.1 Which icon Chrome picks — **VERIFIED**

`components/webapps/browser/android/add_to_homescreen_data_fetcher.cc` (Chromium `main`):

```cpp
InstallableParams ParamsToFetchPrimaryIcon() {
  InstallableParams params;
  params.valid_primary_icon = true;
  params.prefer_maskable_icon = true;      // ← maskable wins over any
  params.fetch_favicon = true;
  return params;
}
```

and the field it feeds, `components/webapps/browser/installable/installable_params.h`:

```cpp
// Whether to prefer an icon with purpose 'maskable' for the primary icon.
// An icon with purpose 'any' is still required for a valid manifest.
bool prefer_maskable_icon = false;
```

Size selection is `blink::ManifestIconSelector::FindBestMatchingIcon`
(`third_party/blink/public/common/manifest/manifest_icon_selector.h`): eligible icons must list the
requested `purpose`, must be square (`max_width_to_height_ratio = 1.0`), and *"If no icon of the ideal
size is found, we will prefer the closest larger-than-ideal image within bounds, followed by the
closest smaller-than-ideal image within bounds."* Ideal sizes come from resources
(`getIdealHomescreenIconSizeInPx`, `getIdealAdaptiveLauncherIconSizeInPx`).

⇒ With our manifest, **the primary/launcher icon is `icon-maskable-512.png`** — the only maskable
entry, and comfortably ≥ ideal. Also relevant: the fetcher notes *"WebAPKs should always use the raw
icon for the launcher whether or not that icon is maskable"* — the bytes we ship are the bytes that
get minted.

### 3.2 What composites the white — **VERIFIED, and it is not the launcher**

The WebAPK shell APK template declares its own launcher icon
(`chrome/android/webapk/shell_apk/AndroidManifest.xml`: `android:icon="@mipmap/ic_launcher"`), and on
API 26+ that resolves to `res/mipmap-anydpi-v26/ic_launcher.xml`:

```xml
<adaptive-icon xmlns:android="http://schemas.android.com/apk/res/android">
    <background android:drawable="@color/white_adaptive_ic_launcher_background"/>
    <foreground android:drawable="@mipmap/maskable_app_icon"/>
</adaptive-icon>
```

`res/values/colors.xml`: `<color name="white_adaptive_ic_launcher_background">#FFFFFF</color>`.

**That is the white box.** The manifest's `background_color` is nowhere in this path — the WebAPK's
adaptive-icon background layer is a hard-coded white resource in the shell template, and our maskable
PNG supplies only the **foreground**. Any transparent pixel in the foreground shows white.
*(Pre-26, `res/mipmap-hdpi/ic_launcher.xml` is a plain `<bitmap android:src="@mipmap/app_icon_hdpi"/>`
— the `any` icon, legacy, which then hits §3.3's launcher wrapper instead.)*

### 3.3 The second white source: the AOSP launcher's legacy wrapper — **VERIFIED**

For icons that are *not* adaptive (plain bitmap shortcuts — Chrome's non-WebAPK "Add to Home screen",
bookmark tiles), the launcher itself wraps them. AOSP
`frameworks/libs/systemui/iconloaderlib/.../BaseIconFactory.java` (`main`):

```java
private static final int DEFAULT_WRAPPER_BACKGROUND = Color.WHITE;
…
public AdaptiveIconDrawable wrapToAdaptiveIcon(@NonNull Drawable icon, @Nullable RectF outIconBounds) {
    if (icon instanceof AdaptiveIconDrawable aid) { return aid; }        // already adaptive → untouched
    EmptyWrapper foreground = new EmptyWrapper();
    AdaptiveIconDrawable dr = new AdaptiveIconDrawable(
            new ColorDrawable(mWrapperBackgroundColor), foreground);      // ← white
    …
}
```

Note the first branch: an icon that is **already** an `AdaptiveIconDrawable` is returned untouched, so
the launcher does *not* add white to adaptive icons. And `Icon.createWithAdaptiveBitmap` produces
`new AdaptiveIconDrawable(null, new BitmapDrawable(…))` — a **null** background layer
(`frameworks/base/graphics/java/android/graphics/drawable/Icon.java`, **VERIFIED**). In other words:
on the *shortcut* path a transparent maskable icon can stay transparent on a stock launcher; on the
*WebAPK* path it cannot, because the shell APK supplies white itself.

### 3.4 The geometry Chrome applies — **VERIFIED (client constants)**

`components/webapps/browser/android/java/.../WebappsIconUtils.java`:

```java
private static final float MASKABLE_SAFE_ZONE_RATIO   = 4.0f / 5.0f;      // web spec: 0.8 diameter
private static final float ADAPTIVE_SAFE_ZONE_RATIO   = 66.0f / 108.0f;   // Android adaptive icon
private static final float MASKABLE_TO_ADAPTIVE_SCALING_FACTOR = MASKABLE_SAFE_ZONE_RATIO / ADAPTIVE_SAFE_ZONE_RATIO;
private static final float MASKABLE_ICON_PADDING_RATIO = (MASKABLE_TO_ADAPTIVE_SCALING_FACTOR - 1.0f) / 2.0f;
```

with the comment: *"The web standard for maskable icons specifies a larger safe zone inside the icon
than Android adaptive icons define. Therefore we need to pad the image so that the maskable icon's
safe zone is reduced to the dimensions expected by Android."*

Working the numbers for a web icon of width **W**:

| Quantity | Value |
|---|---|
| Scaling factor | (4/5) ÷ (66/108) = **1.3091** |
| Padded adaptive canvas `A` | 1.3091 W (padding 15.45 % per side) |
| Android mask **viewport** (72/108 of A) | **0.873 W** — always inside our image |
| Android **guaranteed** circle (66/108 of A) | 0.800 W — exactly the web safe zone ✔ |

**Consequence (the load-bearing one):** the visible masked area is only **87.3 %** of our 512 px
image, entirely inside it. A full-bleed opaque background on our PNG therefore covers **every visible
pixel** of the launcher tile — the white background layer can never show. The transparent ring Chrome
adds outside `0.873 W` is beyond any mask.

⚠ These constants are the *client-side* ones (used for the shortcut path and the install-dialog
preview). The actual WebAPK is minted by a **closed Google server** from the raw web bytes (the shell
manifest comments confirm hashes are taken *"of the icons as they are available on the web"*), so that
the server applies the *same* padding is **REPORTED-by-symmetry, not verified**. It does not change the
recommendation: the spec's safe-zone guarantee holds regardless of how much padding is added.

## 4. Does Firefox for Android honour `purpose: maskable`? (Q2) — **YES, VERIFIED**

Current mozilla-central (`mobile/android/android-components`, fetched 2026-08-11).

**Selection — maskable is ranked first**
(`browser/icons/.../pipeline/IconResourceComparator.kt`):

```kotlin
override fun compare(resource: IconRequest.Resource, other: IconRequest.Resource) = when {
    resource.url == other.url -> 0
    resource.maskable != other.maskable -> -resource.maskable.compareTo(other.maskable)   // maskable first
    resource.type != other.type -> -resource.type.rank().compareTo(other.type.rank())     // MANIFEST_ICON=20
    resource.maxSize != other.maxSize -> -resource.maxSize.compareTo(other.maxSize)       // then largest
    …
}
```

**Filtering + the colour it carries** (`browser/icons/.../extension/WebAppManifest.kt`):

```kotlin
fun WebAppManifest.toIconRequest() = IconRequest(
    url = startUrl,
    size = if (SDK_INT >= Build.VERSION_CODES.O) LAUNCHER_ADAPTIVE else LAUNCHER,
    resources = icons.filter { Purpose.MASKABLE in it.purpose || Purpose.ANY in it.purpose }
                     .map { it.toIconResource() },
    color = backgroundColor,          // ← the manifest's background_color
)
```

**The shortcut it builds** (`feature/pwa/.../WebAppShortcutManager.kt`):

```kotlin
internal suspend fun buildIconFromManifest(manifest: WebAppManifest): IconCompat {
    val icon = icons.loadIcon(manifest.toIconRequest()).await()
    return if (icon.maskable) IconCompat.createWithAdaptiveBitmap(icon.bitmap)
           else IconCompat.createWithBitmap(icon.bitmap)
}
```

⇒ Firefox installs a **pinned launcher shortcut** (`ShortcutInfoCompat` → `WebAppLauncherActivity`),
not a WebAPK. It parses `purpose`, prefers maskable, and marks the icon adaptive.

## 5. What Firefox composites — and the diagnosis that falls out

### 5.1 It fills with `background_color` — **VERIFIED**

Processor order in `webAppIcons(...)`: `MemoryIconProcessor → ResizingProcessor → **ColorProcessor** →
**AdaptiveIconProcessor**`.

`ColorProcessor.kt`:

```kotlin
if (icon.color != null) return icon
// Some PWAs just set the background color to white (such as Twitter, Starbucks)
// but the icons would work better if we fill the background using the Palette API.
if (request.color != null && request.color != Color.WHITE) return icon.copy(color = request.color)
val swatch = Palette.from(icon.bitmap).generate().dominantSwatch
return swatch?.run { icon.copy(color = rgb) } ?: icon
```

`AdaptiveIconProcessor.kt` — same safe-zone maths as Chrome, plus the fill:

```kotlin
private const val MASKABLE_ICON_SAFE_ZONE   = 4 / 5f
private const val ADAPTIVE_ICON_SAFE_ZONE   = 66 / 108f
private const val TRANSPARENT_ICON_SAFE_ZONE = 192 / 176f     // non-maskable: shrink much harder
…
val paddedBitmap = createBitmap(rawIconSize, rawIconSize).applyCanvas {
    icon.color?.also { drawColor(it) }        // ← solid fill behind everything
    drawBitmap(originalBitmap, null, maskBounds, paint)
}
return icon.copy(bitmap = paddedBitmap, maskable = true)
```

Note the last line: on API 26+ **every** web-app icon comes out `maskable = true` (padded), so Firefox
always ships an adaptive icon; and `request.color` is our `#0a0a0d`, which is neither null nor white,
so the fill is `#0a0a0d`.

### 5.2 Answering Q1 per path

| Path | Transparent installed icon possible? | What composites | Backdrop colour |
|---|---|---|---|
| **Chrome → WebAPK** | **No** | the **WebAPK shell's own adaptive-icon background layer** (minted APK resource) | hard-coded **`#FFFFFF`** |
| Chrome → plain shortcut (WebAPK minting unavailable) | maskable: technically yes on a stock launcher (`AdaptiveIconDrawable(null, …)`); non-maskable: no | the **launcher** (`BaseIconFactory` legacy wrapper) | `Color.WHITE` (OEM launchers vary) |
| **Firefox for Android** | **No** | **the browser**, before the shortcut is created (`AdaptiveIconProcessor`) | manifest **`background_color`** → `#0a0a0d` |
| Bookmark / `rel=icon` tile | launcher-dependent | the launcher, if it wraps legacy icons | white on stock Launcher3 |

### 5.3 Therefore: the install was Chrome (inference from the above, not observed)

Firefox cannot produce a white backdrop for *this* manifest — it composites onto `#0a0a0d`. The
observed white box is exactly the WebAPK shell's `#FFFFFF` background layer. Additionally, the owner's
*bookmark* icon rendered borderless, which says the device's launcher does **not** white-wrap legacy
bitmap icons — consistent with the white coming from the WebAPK's own APK resource (launcher
independent) rather than from the launcher. **Conclusion: the installed app is a Chrome WebAPK.**

## 6. `any` transparent + `maskable` opaque, or both opaque? What the field ships (Q4)

**Measured 2026-08-11 by downloading the actual PNGs (VERIFIED — corner alpha + opaque-pixel fraction).**

| Project | `any` icon | `maskable` icon | Art / canvas (maskable) |
|---|---|---|---|
| **X (Twitter)** — `x.com/manifest.json` | 512²: corners **α=0**, 32.8 % transparent | 512²: **100 % opaque**, corners `#000000` | **0.615** |
| **Squoosh** (Google Chrome Labs) | 1024²: corners **α=0**, 21.3 % transparent | 1024²: **100 % opaque**, corners `#3D3F3F` | **0.598** |
| **LibreChat** (demo.librechat.ai) | 192²: **opaque white** | 512²: **100 % opaque** | full-bleed art |
| **ntfy** | 512²: transparent (4.5 %) | **none declared** | — |
| **AnythingLLM** (repo manifest) | one `favicon.png`, `sizes:"any"` | **none declared** | — |
| **open-webui** (`static/static/site.webmanifest`) | — (both entries declared `maskable`) | 512²: **corners α=0, 20.8 % transparent** ⚠ | — |

**Reading:**

- The two projects that clearly got it right (X, Squoosh) both ship exactly the split web.dev
  recommends: **`any` transparent, `maskable` full-bleed opaque**, with the mark at **~0.60** of the
  canvas — noticeably smaller than our 0.779.
- **Correction to a plausible premise:** "make both opaque" is *not* the field norm; LibreChat does it,
  but it also ships an opaque-white 192 `any` which is precisely the look web.dev warns about.
- **⚠ open-webui is a live counter-example, i.e. the same bug we have:** its bundled manifest declares
  **both** icons `purpose: maskable` while the PNG has fully transparent corners — an open-webui
  install on Android renders the same white box. (Its *runtime*-served `/manifest.json`
  — `backend/open_webui/main.py` — instead points both `any` and `maskable` at `/static/logo.png`,
  which is opaque **white** 500².) In-class peers are not a model here.
- Answer to "does the owner then see a dark square?" — **no square.** On Android 8+ an adaptive icon is
  always masked to the launcher's shape (circle/squircle/rounded-square), so a full-bleed `#0a0a0d`
  maskable reads as a **dark squircle with the blue disc inside**, the same silhouette every other app
  on the home screen has. And no path we found renders our `any` icon on the launcher when a maskable
  exists (Chrome prefers it; Firefox sorts it first), so keeping `any` transparent costs nothing.

## 7. Android 13+ themed icons / `monochrome` (Q5) — **not worth shipping**

- **Chrome/WebAPK: no support for the launcher icon.** The shell APK's adaptive icon has exactly two
  layers (`<background>`, `<foreground>`) and **no `<monochrome>`** element; `res/` has only
  `mipmap-anydpi-v26/ic_launcher.xml`, and neither the shell `AndroidManifest.xml` nor
  `shortcut_info.h` carries any monochrome field (`is_primary_icon_maskable` /
  `is_splash_image_maskable` are the only purpose flags). `WebappsIconUtils` defines
  `getIdealMonochromeIconSizeInPx()` but nothing in the WebAPK path consumes it. **VERIFIED** against
  Chromium `main`, 2026-08-11.
- **Firefox for Android: parses it, uses it for one thing that is not the launcher.**
  `WebAppManifest.toMonochromeIconRequest()` has exactly one caller in the tree —
  `feature/pwa/.../WebAppSiteControlsFeature.kt`, the "site controls" notification shown while a PWA is
  open. **VERIFIED.**
- The spec's own framing (§2.4) is "badge or pinned icon with a solid fill", not "adaptive icon
  monochrome layer".
- **Verdict:** shipping a `monochrome` icon buys nothing today on either of the owner's browsers. It is
  a ~10-line generator addition whenever a browser starts wiring it to `<monochrome>`; revisit then.

## 8. iOS `apple-touch-icon` (Q6)

**Current state (VERIFIED, `frontend/index.html`):** `<link rel="apple-touch-icon"
href="/icon-192.png" />` — a transparent PNG.

**Behaviour — REPORTED, not verified against an Apple normative statement.** I read Apple's archived
*Safari Web Content Guide → "Specifying a Webpage Icon for Web Clip"* end-to-end: it covers the link
element, `sizes` and the size-selection fallback, but says **nothing about transparency or alpha**.
The claim is nonetheless the industry-standard one, e.g. RealFaviconGenerator's *"Apple touch icon
turns black"* (fetched 2026-08-11):

> The reason: **iOS forbids transparent icons**. And it must have listened for the Rolling Stones hit
> for too long because **it fills the gaps with black**. Bottom line: do not use transparency in your
> Apple Touch icon.

corroborated by an Apple Developer Forums thread ("Website icon with transparent background becomes
black", thread 713895) and many downstream bug reports. **Recommended fix is the same shape as
Android's: bake an opaque background into a dedicated apple-touch icon.** iOS masks corners
(rounded-rect) rather than cropping aggressively, so the art can sit larger than in the maskable
variant.

```js
// solid fill of its choice, and Chrome's WebAPK shell hard-codes that fill to #FFFFFF.
async function writeIcon(size, scale, outName, bg = { r: 0, g: 0, b: 0, alpha: 0 }) {
  …
  await sharp({ create: { width: size, height: size, channels: 4, background: bg } })
    .composite([{ input: resized, gravity: "center" }])
  …
}

const INK = { r: 0x0a, g: 0x0a, b: 0x0d, alpha: 1 };   // == manifest background_color/theme_color

await writeIcon(48,  0.96, "icon-48.png");
await writeIcon(192, 0.96, "icon-192.png");
await writeIcon(256, 0.96, "icon-256.png");
await writeIcon(512, 0.96, "icon-512.png");
// Maskable: FULL-BLEED opaque + art inside the 80 %-diameter safe zone. 0.62 (not the legal maximum
// 0.78) matches what shipped maskable icons actually do — X 0.615, Squoosh 0.598 (R28 §6).
await writeIcon(512, 0.62, "icon-maskable-512.png", INK);
// iOS composites transparent apple-touch-icons onto BLACK; bake the background in (R28 §8).
await writeIcon(180, 0.75, "apple-touch-icon-180.png", INK);
```

*(Two mechanical notes: `sharp`'s `create.background` takes `alpha` in 0–1, and the inner `resize`
call should keep its transparent `background` — the fill belongs to the canvas, not the contain-pad.)*

### 9.3 Why `#0a0a0d` and not a brand blue or white

- **`#0a0a0d` = the manifest's own `background_color`/`theme_color`** (a documented mirror of cosmos
  `--bg`, `frontend/src/themes/cosmos/tokens.css:17`). One literal, already in the codebase, and it
  makes the launcher tile continuous with the splash screen the app opens into.
- **Brand blue is the one bad choice here:** the mark *is* a blue disc. A blue backdrop erases the
  disc's edge and leaves a floating cat outline.
- **White** is what we're removing; it also fights every other surface in a dark-themed app.
- **Known caveat:** the disc's outline is black ink, so on near-black it stops reading as an outline —
  the blue disc simply floats on dark. On the reference maskable icons this is exactly the look
  (X: white bird-glyph era logo on pure black). If the owner wants edge separation, the drop-in
  alternative is a hair lighter (e.g. `#14141a`); **do not** introduce a new token for it — pick one
  literal and comment it against `--bg`.

### 9.4 What the owner should expect to SEE, per path

| Path | Before | After |
|---|---|---|
| **Chrome WebAPK** (the current install) | blue cat on a **white** squircle | blue disc on a **near-black** squircle, mark ~71 % of the tile (was ~89 %) |
| **Firefox for Android** install | blue cat on a **`#0a0a0d`** squircle (already dark; Firefox filled it) | visually ~the same, now baked in rather than browser-supplied — consistent across both browsers |
| **Bookmark / home-screen shortcut** (`rel=icon` 48/192) | unchanged | unchanged — still the raw transparent PNGs |
| **In-app / tab / desktop install** | unchanged | unchanged — `any` icons untouched |
| **iOS add-to-home-screen** | cat on **black** (accidental) | cat on `#0a0a0d`, deliberate — *only if the optional apple-touch file lands* |

### 9.5 Re-install / cache gotchas — **VERIFIED**

1. **An already-minted WebAPK does not pick up a changed icon immediately.** Chrome checks a WebAPK's
   manifest at most once per launch-day: `WebappDataStorage.UPDATE_INTERVAL = DateUtils.DAY_IN_MILLIS`,
   with `RELAXED_UPDATE_INTERVAL = 30 days` for apps it has decided to relax
   (`shouldCheckForUpdate()`).
2. **When it does notice, it asks.** `WebApkUpdateManager` computes `PRIMARY_ICON_HASH_DIFFERS` from the
   murmur2 hash of the *raw web bytes* and then:
   `boolean showDialogForIcon = iconChanging && !iconChangeBelowThreshold;` → an **App Identity Update
   dialog** the owner must approve, unless the same change was approved before
   (`getLastWebApkUpdateHashAccepted()`). Only after approval is the WebAPK re-minted and silently
   re-installed.
3. **Deterministic path:** long-press → uninstall the ctrl-b app icon, hard-reload the site in Chrome
   (so the new PNG bytes are fetched), then install again. The murmur2 hash is taken of the file *as
   served*, so make sure the new bytes are actually on the wire — the icons live in `public/` and are
   **not** in the workbox precache (`globPatterns: ["**/*.{js,css,html}", "assets/vapor-logo-*.png"]`),
   and ctrl-b sets no explicit `Cache-Control` on dist files, so a normal revalidation suffices; a
   stale HTTP cache entry is the only thing to rule out.
4. Filename-busting (`icon-maskable-512-v2.png` + the manifest `src`) would sidestep both the HTTP cache
   and any hash confusion, at the cost of a manifest edit. Not needed if the owner is reinstalling
   anyway.

## 10. What I could NOT determine

1. **Which browser actually performed the install** — §5.3 is a strong *inference* from the colours the
   two code paths can produce, not an observation. A 5-second check settles it: Android Settings → Apps
   → look for a "ctrl-b" entry whose installer/package name looks like
   `org.chromium.webapk.*` (WebAPK) vs no app entry at all (Firefox pins a shortcut, not an app).
2. **The WebAPK minting server's exact icon processing.** It is closed-source Google infrastructure.
   That it applies the same `MASKABLE_ICON_PADDING_RATIO` as the client constants is inferred from the
   client comments and the shell template, not verified. The safe-zone guarantee makes the
   recommendation robust either way.
3. **What `@mipmap/maskable_app_icon` contains when a site ships *no* maskable icon.** The shell's
   adaptive XML references it unconditionally while the meta-data is mustache-gated
   (`{{#has_maskable_icon}}`), so the server must synthesise one; how, is unknown. Irrelevant for us —
   we ship a maskable icon.
4. **An Apple normative statement on `apple-touch-icon` transparency.** The archived Safari Web Content
   Guide is silent; the HIG page is JS-rendered and did not yield text. §8 is REPORTED.
5. **Why the owner's pre-install bookmark icon rendered borderless.** On stock Launcher3 a legacy
   bitmap shortcut *should* get the white wrapper (§3.3). That it didn't suggests a non-AOSP launcher
   (Samsung One UI, MIUI and others have their own icon-frame policies) — I could not identify the
   device's launcher, and OEM launcher behaviour with transparent/adaptive icons is **UNVERIFIED**.
   It does not change the recommendation (the WebAPK white is launcher-independent), and it is
   consistent with §5.3.
6. **Whether any launcher's parallax/zoom can reveal the transparent ring** Chrome adds outside
   `0.873 W`. Outside every mask by construction, but "MAY apply a mask of any size" leaves room.
   Unlikely to matter; would show as a thin white/transparent halo if it ever did.
7. **Which icon Chrome picks for the *splash* image** (`splash_image_url` / `is_splash_image_maskable`
   are separate fields). Either answer is fine for us: the splash draws over `background_color`
   `#0a0a0d`, so both a transparent `any` cat and a full-bleed `#0a0a0d` maskable disappear into the
   same background.
8. **Live device confirmation of the after-state.** Everything above is source- and pixel-level; the
   final acceptance is still an eyeball round on the phone after a reinstall.

## 12. Addendum — 2026-08-18 (the W5/D59 build pass)

Three corrections/additions found while building the selector. §9's *recommendation* stands; what
changed is the **update mechanics** §9.5 described, and one claim in it was wrong.

### 12.1 Chrome 144 (2026-01-21) supersedes §9.5.1–2 — **manifest icon URLs are now immutable**

Chrome's web-app update path was reworked. The three changes that matter here:

1. **A manifest icon URL is treated as immutable.** Chrome no longer re-fetches the bytes at a URL it
   has already minted an app from — so *repainting a file in place is a no-op for every installed
   app*, whatever the murmur2 hash of the new bytes would be. §9.5.3's "make sure the new bytes are
   actually on the wire" is now beside the point: the bytes are never asked for again.
2. **A CHANGED icon URL is the trigger**, and it is no longer throttled to
   `UPDATE_INTERVAL = DAY_IN_MILLIS`.
3. **The blocking App Identity Update dialog is gone**; a changed identity now surfaces as a
   **"Review app update" suggestion in the installed app's ⋮ menu**, which the owner approves at
   leisure. (Older Chrome keeps the daily-ish check and the dialog — hence the Conf row's copy
   covering both.)

Source: <https://developer.chrome.com/blog/improvements-to-web-app-updates> (REPORTED — the blog
post; the Chromium-side constants were not re-read for this addendum).

**Consequence, and the reason D59 exists:** an owner-selectable backdrop *cannot* be a repaint of
`icon-maskable-512.png`. The variant must live in the **URL**, which means the manifest must vary per
selection, which means it cannot be served as a static build artifact. `/manifest.webmanifest` is now
a backend route (`backend/app/main.py` → `app/core/pwa.py`). It also makes the "stay on Clear" case
free: same filename **and** same bytes ⇒ nothing for Chrome to review, ever.

### 12.2 Correction — the icons **are** workbox-precached (§9.5.3 was wrong)

§9.5.3 claimed the icons are outside the precache because `globPatterns` lists only
`**/*.{js,css,html}` + the vapor logo. That reading missed `vite-plugin-pwa`'s
**`includeManifestIcons`, which defaults to `true`**: every file named in the `manifest.icons` block
is added to the precache manifest independently of `globPatterns`. The built `dist/sw.js` confirms
it — the icon entries are in the precache list.

Practical effect for W5: the four NEW variants are deliberately **not** in the manifest block (only
the stable maskable file is), so they are not precached and cost no install anything; they are
fetched from the network when the WebAPK minting server asks for the one the manifest currently
names. `vite.config.ts` is therefore left untouched by D59 — the rewrite happens server-side.

### 12.3 Confirmation — Chrome uploads the icon BYTES to the minting server

`webapk.proto`'s `Image` message carries an `image_data` field (image bytes, possibly re-encoded by
Chrome) alongside `src` and `hash`. So the minting server is handed the image by the browser rather
than fetching the URL itself — which is why WebAPK minting works at all for a **tailnet-only** origin
like ctrl-b, where Google's infrastructure could never reach `emma.lobster-vector.ts.net`. Recorded
because §10's "closed-source minting server" gap invited the opposite assumption, and because it means
the icon a phone mints comes from the image fetched and processed by THAT phone: the tailnet is the
only fetcher.
